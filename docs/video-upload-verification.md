# 영상 업로드 검증 기록

관련 이슈는 #612이다. 검증일은 2026-11-15이며 백엔드 작업의 범위와 프론트 연동 과제를 구분한다.

## 자동화 검증

JDK 21에서 CI와 같은 `./gradlew spotlessCheck clean build --no-daemon`을 실행하고 실행 JAR에 Flyway SQL이 포함되는지 확인한다.

| 범위 | 검증 내용 |
| --- | --- |
| 업로드 | 용도·신고 크기 경계값, 실제 크기·MIME, 원본/썸네일 누락, 저장소 오류, 다른 저장소·경로 거절 |
| 전시 | 구형/신형 요청, 최종 영상 개수, 대표·추가 간 영상 이동, 크롭 초기화, 실패 후 기존 상태 보존, 행 ID 유지 |
| 작품 | 구형 요청, 등록·상세·수정 복원, 영상↔이미지, 개수·작업 과정 제한, 기존 영상의 이미지 재분류 거절, 권한 거부 |
| 조회 | 홈·검색·지도·내 전시·작가·저장·초대·작품 카드의 썸네일, 주요 목록의 영상 URL, 캐시 갱신 |
| 관리자 | 심사 상세의 기존 이미지 목록과 원본·타입·썸네일 목록 정렬 및 HTTP 변환 |
| 문서 | 실제 /v3/api-docs의 전시·작품 미디어 스키마와 고유한 응답 이름 |
| 파일 정리 | DB 커밋/롤백, 원본과 썸네일, 공유 참조, URL 별칭, 실패 시 보존과 최대 3회 재시도 |

작품 HTTP 통합 테스트는 저장소 확인만 모의 처리한다. 사용자·전시·작품·작가 연결은 실제 테스트 DB를 사용한다. H2 자동 생성에서 같은 테이블의 쓰기/읽기 매핑이 분리되는 것을 막기 위해 해당 테스트만 식별자 인용을 통일하고 User·Creator의 자동 번호 열을 실제 스키마에 맞춘다. 운영 DB 매핑과 공통 테스트 설정은 변경하지 않는다.

## 실제 MySQL과 Flyway

기존 로컬 MySQL 8.4 이미지를 재사용한 별도 컨테이너에서 Flyway 11.14.1을 실행했다.

- 기존 83개 마이그레이션 적용 후 구형 DisplayImage와 ArtworkImage를 삽입했다.
- 신규 2개 적용 후 원본 URL 보존, mediaType=IMAGE, thumbnailUrl=null을 확인했다.
- VIDEO 원본·썸네일 저장과 조회를 확인했다.
- 이력 85개와 체크섬 검증을 통과했고 재실행은 추가 적용 0개였다.
- 실제 JdbcMediaReferenceQuery로 전시·작품의 원본/썸네일, 삭제된 부모, 프로필의 별칭 URL, 해석이 불명확한 호스트 URL의 보존 처리를 확인했다.
- 태스크 컨테이너와 임시 볼륨은 제거했다. 기존 컨테이너와 저장 볼륨은 유지했다.

## 실제 저장소와 브라우저

개발용 저장소에서 애플리케이션의 URL 발급·객체 검증 서비스를 사용했다. 전시/작품 각각 MP4·MOV·WEBM을 PUT하고 CDN에서 바이트와 Content-Type을 확인했다. Range 요청은 206을 반환했고 프론트 출처의 CORS 응답을 확인했다. 썸네일 누락과 신고 용량 초과 거절도 확인했다.

이 검증은 실행 중인 dev HTTP API를 호출한 배포 검증은 아니다. 변경 코드를 로컬에서 실행해 실제 dev S3·CDN과 연결한 검사다. 사용한 작은 영상과 썸네일 총 8개는 검증 후 삭제하고 저장소의 잔여 객체 0개를 확인했다.

Chrome 157에서 H.264 MP4/MOV, VP9 WEBM의 1초 샘플을 로컬 HTTP로 제공해 끝까지 재생했다. 각 샘플은 160×90이며 S3 검사와 같은 파일이다. 실제 서비스의 자동 재생 UI, Safari, iOS, Android 또는 모든 내부 코덱을 검증한 결과는 아니다.

## 파일 정리의 보장 범위

전시·작품에서 교체하거나 삭제한 파일을 DB 커밋 후 처리한다. 현재 전시·작품의 원본/썸네일 참조와 사용자·작가·칼럼·전시 콘텐츠·개인 작품·라운지·후기·작품 대화 이미지의 URL 필드를 검사한다. 다른 영역의 삭제된 행도 보수적으로 참조로 간주할 수 있다.

참조 검사 실패나 해석할 수 없는 URL은 삭제를 중단한다. 따라서 일부 잘못된 외부 URL도 후보 파일의 보존을 유발할 수 있다. 참조 검사는 기존 URL 열을 검색하므로 데이터가 커지면 비용이 증가한다. 별도의 파일 참조 인덱스나 업로드 원장은 도입하지 않았다.

삭제 실패는 최대 3회 시도하고 최종 실패 URL을 로그에 남긴다. 로그는 query·fragment·사용자 인증 정보를 제외한다. 운영자는 최종 실패 URL을 모아 동일한 참조 검사와 삭제 경로로 재처리해야 한다. 영속 실패 큐나 자동 스케줄러는 없다. 프로세스 중단으로 커밋 후 이벤트가 유실되는 경우도 자동 복구하지 않는다.

참조 확인 직후 다른 요청이 같은 파일을 첨부하는 경쟁 상태는 막지 못한다. 이를 보장하려면 모든 첨부 경로가 공유하는 파일 소유권·수명 상태가 필요하다. 등록되지 않은 업로드는 보존한다. 전체 images/ 또는 videos/ 경로에 만료 규칙을 걸지 않는다.

## 배포 전에 남은 연동 검증

- 프론트의 30초/180초 길이 제한, 썸네일 생성·재업로드, 작성 취소와 등록 재시도.
- 실제 전시 화면의 무음 반복 재생, 캐러셀 이동 시 정지, 자동 재생 차단과 실패 안내.
- 서비스가 지원할 모바일·Safari 및 내부 코덱 범위.
- 배포된 API와 프론트의 최종 연동 확인 후 영상 입력 노출.

서버 HEAD 검사는 등록 시점의 파일 크기와 메타데이터를 확인한다. 실제 코덱·길이·사용자별 파일 소유권을 보장하지 않으며, presigned PUT 만료 전 재업로드로 등록 후 파일이 변경되는 것도 막지 못한다.
